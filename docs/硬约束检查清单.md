# 硬约束检查清单

《开发上下文》§0.5 写的是：**第 8 章每一条都应当有对应的自动化检查。**

这份清单把 C1–C13 逐条对到实现与检查上。
跑 `npm run check:constraints` 会一次跑完 15 项，全绿才算过。

## 哪些不是自动的

以下三条**不能**靠静态扫描保证，靠的是集成测试与人工：

| 事项 | 怎么保证 |
|---|---|
| 环节实耗真的等于真实上课时间 | `tools/smoke-test.mjs` 验证「进行中的环节自动累计」；课后再人工看一节课的时间轴 |
| 可见性越权返回 404 | `tools/smoke-test.mjs`：家长读别人的孩子 → 404；未登录 → 401 |
| 插件回传真的落成作品 | `tools/smoke-test.mjs`：回传 → `artifact` + `showcase` 生成 |

**「课堂断网时活动仍可完成、结果恢复后补传」需要一次实机演练**
（设计方案 §9.2 的 V1 验收项）。代码里已有本地队列与自动补传逻辑，
但断网演练要在一台真机上做，仓库里做不了。

## 怎么跑

```bash
npm run check:constraints   # 15 项硬约束检查
npm run verify              # typecheck + 单元测试 + 硬约束检查
node tools/smoke-test.mjs   # 34 项端到端冒烟（需先启动后端）
```

硬约束检查失败会列出**文件 + 行号 + 命中的词**，直接定位。

---

## 加一条新约束的做法

1. 在《开发上下文》第 8 章加一行，给它一个编号
2. 在 `packages/shared/src/copy.ts` 或对应模块落实
3. 在 `tools/check-constraints/run.mjs` 加一个 `check('C14', '…', (p) => {…})`
4. 在本文件补一行
5. 跑 `npm run check:constraints` 确认它真的会失败 —— **一个永远不会失败的检查等于没有检查**
