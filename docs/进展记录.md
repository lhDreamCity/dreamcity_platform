## 2026-11-18 · 腾讯云短信接入（代码侧全部就绪，等腾讯云侧）

### 做了什么

**修掉一个会让真实发送必崩的 bug**：`packages/server/src/lib/sms.ts` 里从 SDK 取
构造器写的是 `mod.SmsClient`，但这个包的导出形状是 `sms.v20210111.Client`
（见 `node_modules/tencentcloud-sdk-nodejs-sms/tencentcloud/services/index.d.ts`）。
而且 SDK 压根没装 —— `package-lock.json` 里搜不到 `tencentcloud-sdk-nodejs-sms`。
两件事叠在一起，`SMS_DRIVER=tencent` 第一次发短信就崩。

**坑 A：发送失败被静默吞掉。** 原代码 `await client.SendSms(...)` 之后不检查返回值，
直接 `return { ok: true }`。腾讯云有两层错误：

| 层 | 位置 | SDK 行为 |
|---|---|---|
| 顶层 | `Response.Error`（密钥错、模板不存在、签名没审过） | **会抛异常** |
| 逐条 | `SendStatusSet[].Code`（限流、模板不符…） | **不抛** |

漏看第二层 = 短信根本没发出去，家长端却显示「验证码已发送」，问题一路拖到
真实家长登录不了才暴露。

按鲁棒性原则修了四件事：

1. 两层错误都查，失败抛 `SmsSendError`（带腾讯云错误码）；
2. **发送成功才写缓存** —— 原来先写缓存再发，失败时家长收到一个永远收不到的
   验证码，还被锁 60 秒；现在失败不占冷却、立刻能重试；
3. `SMS_DRIVER=tencent` 但配置缺项 → **拒绝启动**（不是警告）；
   理由：缺项时服务能起来、家长却永远收不到短信，比不配更危险；
4. 错误码进服务端日志、手机号脱敏（`138****0001`），前端只给人话。

**模板参数个数做成配置项** `SMS_TEMPLATE_PARAM_COUNT`（默认 1）。
腾讯云要求「参数个数 = 模板变量个数」：验证码类模板通常只有 `{1}` 一个变量
（有效期写死在文案里），通用类才有 `{1}{2}`。原来代码把 `TemplateParamSet`
写死成 `[code, '5']`，配单参数模板会被拒发。

**其余配套**：`SMS_SECRET_KEY` 收进正规 env 层（原来在 `sms.ts` 里裸读
`process.env`）；容器显式透传 `SMS_*`（容器读不到主机 `.env`，漏传的表现是
「短信发不出去但服务看着正常」）；前端区分真发短信与开发模式（原来那句
「验证码是 00000」在生产环境也是错的）；生产自检两档行为都实测过。

### 顺带加的部署前置检查

新代码里 `SMS_DRIVER=tencent` 缺项会**拒绝启动**。如果这种配置走到部署之后，
容器起不来 → 平台整体不可用（讲师端也进不去）。

所以加了一道部署前的闸：`deploy/check-env.mjs`（Node 写的，能在本机跑测试）
在 `ci-deploy.sh` 里被调用，检查三件事：

1. 必填项缺失（`POSTGRES_PASSWORD` / `REDIS_PASSWORD` / `JWT_SECRET` / `ADMIN_PASSWORD`）
2. `SMS_DRIVER=tencent` 时短信五项是否齐全
3. **同名变量重复** —— 后者覆盖前者，于是「我改了怎么没生效」

19 项单测覆盖这个检查器（含解析规则与部署脚本调用方式）。
用暂存目录里的新版本（`$STAGE_DIR`），不是服务器上那份旧的。

### ⚠️ 顺带查出来的：Deploy 又失败了（与本次改动无关）

推送后 CI 全绿，但 **Deploy 失败**，失败步骤是「传到服务器并部署」。
和 11-12 那次（`63a0e39`）**失败点完全一样** —— 不是这次改动引起的。

```text
Deploy => failure
   打包（只含 git 跟踪的文件…）  => success
   传到服务器并部署               => failure   ← 挂在这
   线上验收                       => skipped
```

原因几乎可以确定：**4 个 GitHub Secrets 没配**（`DEPLOY_SSH_KEY` / `DEPLOY_HOST` /
`DEPLOY_USER` / `DEPLOY_KNOWN_HOSTS`）。连带地，服务器侧的
`/home/ubuntu/ci-deploy.sh`、`authorized_keys` 里的受限密钥条目、
`.env` 的 `ADMIN_PASSWORD` 也都还没做 —— 这些都是
`tools/setup-ci-deploy.ps1` 一次跑完的事，而那一步从没成功执行过
（脚本第 1 步要 `gh` 登录，本机 `gh` 至今未登录）。

**这意味着：线上仍然是 11-06 那版，本次短信改动也还没上线。**
`/console` 仍能进、3D 插件仍 404。

要推进就在**普通 PowerShell** 里跑（不要在 Claude Code 里跑 —— 私钥与口令
不该经过会记录它们的工具）：

```powershell
powershell -ExecutionPolicy Bypass -File D:\dreamcity_platform\tools\setup-ci-deploy.ps1
```
